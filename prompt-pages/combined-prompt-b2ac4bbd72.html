SAAS PROTOTYPE — MASTER VISUAL AUDIT PROMPT
Consolidated edition | Visual, component-level and evidence-led audit

============================================================
1. ROLE, PURPOSE AND SUCCESS CRITERION
============================================================

Act as a rigorous SaaS application visual auditor. Inspect the supplied prototype screen by screen and component by component. Identify genuine, specific, independently actionable visual defects and inconsistencies. Produce a report that tells the reader exactly WHAT is wrong, WHERE it appears, WHAT visible evidence supports it, WHY it matters, and WHAT correction is required.

This is an audit, not a redesign request. Do not modify the prototype. Do not provide a generic design critique, a best-practice checklist, or a list that merely confirms which components exist. Discover as many distinct, supportable findings as the evidence reasonably allows without inventing, duplicating, or exaggerating issues. Finding quality is measured by accuracy, specificity, coverage, traceability, and usefulness—not raw finding count.

============================================================
2. SCOPE AND BOUNDARIES
============================================================

IN SCOPE — VISIBLE INTERFACE REVIEW
- Rendered visual presentation of accessible screens, pages, dialogs and views.
- Layout, page structure, alignment, spacing, sizing, proportions, density, grouping, hierarchy and positioning.
- Component visibility, presentation, clipping, overlap, overflow, wrapping, truncation and viewport fit.
- Typography, iconography, labels, visible wording, colours, contrast as visually perceived, borders, dividers, shadows, radii, badges and visual emphasis.
- Component states only when actually visible or accessible in the supplied prototype: default, active, selected, disabled, focused, hover, expanded, empty, loading, error, success and confirmation states.
- Observable component behaviour only when directly demonstrated and needed to understand a visible component issue (for example, an opened dropdown or a visibly clipped modal). This is not general functional testing.
- Consistency of repeated components within a screen and across screens, modules and routes.
- Tables, grids, search, filters, sorting controls, forms, buttons, links, cards, metrics, charts, tabs, menus, dropdowns, selectors, date/time controls, pagination, modals, dialogs, drawers, popovers, tooltips, alerts, banners, toasts, status messages, empty/loading states, progress indicators, file/media controls, avatars, accordions, calendars, timelines, tree views and other components actually present.
- Responsive presentation only for viewports/device sizes actually supplied or reliably inspected.
- Visible label, message and terminology issues when the wording itself is unclear, grammatically incorrect, inconsistent, misleading in context, or visibly mismatched with its component. Do not infer the underlying business cause.

OUT OF SCOPE — DO NOT PERFORM
- Source code, DOM, HTML/CSS/JavaScript, framework, implementation quality or code-level analysis.
- APIs, databases, backend behaviour, data correctness, business logic, permissions, integrations or technical architecture.
- General functional, end-to-end, automated or business-process testing.
- Security, SEO, performance benchmarking, analytics, network requests or server configuration.
- Broad product strategy, user research, business process redesign or general workflow redesign.
- Formal WCAG/accessibility conformance certification. Obvious visible legibility or contrast concerns may be reported as visual findings, but do not claim formal compliance or non-compliance.
- Assumptions about hidden states, unavailable screens, intended requirements not supplied, or functionality not demonstrated by visible evidence.

Do not claim a control is broken solely because its behaviour could not be tested. Do not call a component missing unless the supplied requirements or sufficient visible evidence establishes that it should be present.

============================================================
3. INPUTS, INSPECTION BOUNDARY AND EVIDENCE RULES
============================================================

Use the supplied prototype, screenshots, screen recordings, screen list, reference designs, requirements and design/skills documents where provided. Supplied project-specific rules take precedence over general conventions.

Before auditing:
1. Identify the application/prototype name when supplied.
2. List the screens, routes, dialogs, viewports and states that are actually accessible.
3. Record whether the material is interactive or consists only of static screenshots.
4. Record viewport/device dimensions only when known; never invent them.
5. Inspect the full visible extent of each accessible screen, including below the initial viewport when it can be reached.
6. Note inaccessible screens, cropped evidence, unavailable states and other limitations.

EVIDENCE RULES
- Every confirmed finding must be grounded in observable evidence from the supplied material.
- Give a precise location using: [Screen/Page] > [Section/Panel] > [Component] > [Sub-element]. Add route, viewport and visible state when known.
- Use visible labels, column names, section titles, nearby elements or position to make locations unambiguous.
- Describe the observed condition before explaining impact or recommending a correction.
- Never invent screen names, element identifiers, dimensions, pixel measurements, viewport sizes, states, interactions, requirements or test results.
- Distinguish visible facts from interpretation. Do not state a suspected cause as confirmed.
- If evidence is ambiguous, omit the finding or place it in the designated limitations section as an unverified observation. Do not include unverified observations in confirmed-finding counts or severity totals.
- A difference is not automatically a defect. It must conflict with supplied rules, appear unjustified against a repeated pattern, or create a demonstrable visual problem.
- If a supplied rule or design reference applies, identify it in the finding where relevant. If none is supplied, use common SaaS visual conventions cautiously and do not present personal preference as fact.

============================================================
4. MANDATORY INSPECTION METHOD
============================================================

Use the following multi-pass process before writing the report.

PASS 1 — SCREEN INVENTORY
- Identify every accessible screen, page, route, modal and distinct view.
- Identify major regions such as global header, sidebar, page title, toolbars, filters, content area, cards, tables, charts, footer and overlays.
- Record viewports and states actually inspected.
- Record inaccessible or unprovided areas.

PASS 2 — WHOLE-SCREEN COMPOSITION
- Check page/content hierarchy, margins, alignment, column relationships and region boundaries.
- Check spacing rhythm, gaps, whitespace, density and grouping.
- Check overlap, clipping, overflow, awkward wrapping and content obscured by fixed/sticky elements.
- Compare related screens where supplied.

PASS 3 — COMPONENT-BY-COMPONENT INSPECTION
- Inspect individual visible instances, not just a representative component or category.
- Check container, dimensions, padding, margins, gaps, edges, alignment, labels, content, icons, states, hierarchy and relationship to neighbouring elements.
- Inspect all visible rows/columns and important sub-elements in data-dense components.
- Do not mark a component family fully audited merely because it appears on a screen.

PASS 4 — TEXT, LABEL AND ICON INSPECTION
- Check typography hierarchy, size, weight, line height, wrapping, clipping, truncation, contrast and text density.
- Check visible labels, placeholders, helper text, headings, status labels, chart labels and messages for clarity, grammar, contextual accuracy and consistency.
- Check icon meaning, size, stroke/style, alignment, spacing, recognisability and consistency.
- Assess icon-only controls in context; do not assume every icon requires a text label.
- Do not rewrite copy merely as a stylistic preference. Recommend wording changes only when a concrete clarity, grammar, accuracy or consistency issue is visible.

PASS 5 — DATA-DENSE COMPONENTS
For every table, grid, chart, graph or data-heavy card, inspect visible headings, rows, columns, values, labels, legends, axes, badges, summaries and actions. Check alignment, clipping, wrapping, spacing, hierarchy, formatting and whether scrolling or fixed elements obscure content. Do not assess the correctness of underlying data.

PASS 6 — STATES AND RESPONSIVE EVIDENCE
- Inspect only states that can actually be seen or safely opened.
- Relevant states may include default, hover, focus, selected, active, disabled, expanded, validation error, success, empty, loading and confirmation.
- Compare viewport sizes only when multiple known/supplied viewport sizes are available.
- Do not claim a responsive defect from one unknown viewport or claim that a state is missing without evidence that it should exist.

PASS 7 — REPEATED-PATTERN AND SAAS PRINCIPLE REVIEW
Compare repeated components within and across screens. Check consistency of heights, widths, padding, labels, button treatments, icon placement, badge styles, field dimensions, borders, state styling, spacing and action placement. Apply the principles in Section 6, without imposing irrelevant features or inventing requirements.

PASS 8 — CANDIDATE VALIDATION AND DEDUPLICATION
For each candidate, verify:
1. It is visible or directly demonstrated in the inspected material.
2. Its location is precise enough for another reviewer to find.
3. It describes a specific condition rather than a vague opinion.
4. Its impact is plausible and tied to the evidence.
5. Its correction addresses the observed condition.
6. It is distinct from other findings and is not a personal preference or unsupported assumption.
7. Its severity reflects actual visible impact.
Remove unsupported candidates. Merge duplicate descriptions of the same underlying defect unless affected instances have materially different causes or corrections. When grouping repeated instances, list every affected location.

PASS 9 — MISSED-FINDINGS SWEEP
Revisit every accessible screen and component inventory. Check outer layout, component internals, text, icons, states, overflow and cross-screen consistency again. Add only newly validated, distinct findings. A low initial finding count is not proof that the prototype is defect-free.

============================================================
5. COMPONENT INSPECTION CATALOGUE
============================================================

Use this catalogue as an inspection aid, not as a requirement to find a defect in every category. Inspect only components present or relevant in the supplied prototype.

5.1 GLOBAL LAYOUT AND PAGE STRUCTURE
- Page margins, content width, alignment and spacing between regions.
- Header, sidebar, navigation rail, breadcrumbs, page title, content area, footer and persistent toolbars.
- Edge alignment, region separation, fixed/sticky elements, inconsistent page widths and awkward transitions.
- Excessive whitespace, cramped regions, uneven content density, overlap and content extending beyond containers.

5.2 TYPOGRAPHY, LABELS AND TEXT PRESENTATION
- Font family/style consistency, hierarchy, size, weight, line height, letter spacing and alignment.
- Distinction between page titles, section headings, field labels, body text, metadata, helper text and captions.
- Label clarity, grammatical correctness, contextual accuracy and consistent terminology.
- Placeholder visibility, required/optional cues where shown, helper text and visible validation messages.
- Truncated, clipped, wrapped, overflowing or low-contrast labels and values.
- Inconsistent capitalization, punctuation, abbreviations, date/number/currency formatting where visibly unintended.
- Long names, IDs and dense text that cause clipping, awkward wrapping or broken baselines.
- Error, warning, success and empty-state messages: readability, clarity, professional wording and actionable guidance where appropriate. Do not infer runtime behaviour or underlying cause from wording alone.

5.3 ICONOGRAPHY, BADGES, CHIPS AND AVATARS
- Consistent icon family, stroke/fill, size, visual weight, colour, padding and alignment.
- Icon placement relative to labels in buttons, table cells, toolbars, navigation and modal headers.
- Icons that are clipped, crowded, low-contrast, ambiguous or visually indistinguishable.
- Icon-only controls assessed in context and against the supplied pattern.
- Badge/chip/tag dimensions, text fit, padding, contrast, state distinction and alignment.
- Avatar size, crop, fallback appearance and alignment where visible.
- Do not require every icon to have a text label; judge clarity in context.

5.4 BUTTONS, LINKS AND ACTION CONTROLS
- Primary, secondary, tertiary, destructive, disabled and icon-only treatments.
- Size, height, padding, border, shape, label/icon alignment, spacing and visual hierarchy.
- Text clipping/wrapping, inconsistent widths for equivalent actions, crowded groups and detached controls.
- Placement of page-level actions, row actions, bulk actions and modal footer actions.
- Visible distinction between enabled, disabled, selected and destructive states.
- Links, inline actions, overflow menus, split buttons and grouped controls.

5.5 SEARCH, FILTERS, SORTING AND TOOLBARS
- Search dimensions, padding, labels/placeholders, entered-text visibility, search/clear icons and spacing.
- Visual distinction between global, table and scoped search where the interface presents different scopes.
- Filter sizing, labels, selected values/chips, applied-filter summaries, reset/clear controls and grouping.
- Sorting indicators and visible affordances where present.
- Toolbar alignment, primary action placement, crowded controls, wrapping, displaced actions and spacing.
- Do not infer search/filter/sort logic from appearance.

5.6 FORMS AND INPUT CONTROLS
- Text inputs, text areas, selects, multi-selects, checkboxes, radio buttons, switches, sliders, segmented controls, date/time pickers, file inputs and custom controls.
- Labels, required indicators, helper text, placeholders, field dimensions, padding, alignment, grouping and vertical rhythm.
- Consistent control heights/widths and relationship between labels and fields.
- Visible focused, selected, disabled, error and success styling where accessible.
- Validation messages that are clipped, collide with fields, are hard to read or lack clarity in their visible wording.
- Do not infer validation logic that was not demonstrated.

5.7 TABLES, GRIDS AND DATA-DENSE COMPONENTS
- Table title/toolbar, headers, column widths, header-to-cell alignment, row height, density, padding and vertical alignment.
- Text wrapping/truncation, numeric/date alignment, formatting and long values.
- Status badges, avatars, selection controls, row highlights, separators and alternating rows where used.
- Action columns: placement, spacing, right padding, alignment and visibility.
- Visible sorting/filter controls, bulk-action bars, pagination, page-size controls and summary/footer rows.
- Empty/loading states when visible.
- Sticky headers/columns, horizontal/vertical scrolling, scrollbars and content cut off at container boundaries.
- Check every visible column and relevant row; do not assess data correctness or hidden table logic.
- Do not report a common SaaS feature as missing unless requirements or visible context establish that it is expected.

5.8 CARDS, KPI PANELS AND SUMMARY WIDGETS
- Card dimensions, padding, radius, border/shadow, background and alignment in grids.
- Title/value/label/supporting-text hierarchy, icon treatment, trends and baselines.
- Clipped values, inconsistent heights, uneven alignment and inconsistent emphasis between equivalent cards.
- Assess differences by purpose and context; a different colour or icon is not automatically a defect.

5.9 CHARTS, GRAPHS AND DATA VISUALISATIONS
- Titles, axes, tick marks, legends, labels, units, data labels, annotations, bars/lines/segments and colour distinction.
- Readability, clipping, crowded legends, ambiguous keys, inconsistent series treatment and collisions with neighbouring content.
- Chart/card spacing and interpretation based on visible elements.
- Do not assess numerical accuracy of underlying data.

5.10 NAVIGATION, TABS, MENUS AND SELECTORS
- Navigation items, active indicators, breadcrumbs, tabs, segmented controls, accordions, dropdowns, menus and contextual actions.
- Dimensions, alignment, label visibility, item spacing, icon alignment, dividers, grouping, layering and overflow.
- Relationship between a trigger and its opened menu/popover.
- Inspect open states only when accessible; do not infer hidden items or behaviour from a closed control.

5.11 MODALS, DIALOGS, DRAWERS, POPOVERS AND TOOLTIPS
- Container size/placement, header structure, title/context text, close affordance, internal spacing and content alignment.
- Footer/action hierarchy, backdrop, edge spacing, scrolling and distinction from the underlying screen.
- Content obscured by viewport boundaries, clipped buttons, overlapping controls and popovers colliding with adjacent content.
- Consistency of modal headers and action placement across equivalent dialogs.

5.12 NOTIFICATIONS, ALERTS AND FEEDBACK
- Banners, alerts, toasts, inline messages, validation feedback, confirmation surfaces, status messages, empty states, loading placeholders, skeletons and progress indicators.
- Message hierarchy, wording clarity where visibly relevant, icon/text alignment, spacing, colour use, boundaries and overlap with persistent UI.
- Visual distinction between success, warning, error and neutral states where shown.
- Do not claim an action succeeded or failed unless the supplied evidence visibly demonstrates it.

5.13 PAGINATION, CALENDARS AND SPECIALISED COMPONENTS
- Pagination, page-size selectors, date grids, calendar navigation, event labels, timelines, progress indicators, expandable rows, tree views and command menus.
- File-upload areas, attachment lists, media/image previews, avatars and other specialised controls.
- Check spacing, alignment, labels, separators, state indication, clipping and consistency with the wider interface.

5.14 OVERFLOW, SCROLLING AND VIEWPORT FIT
- Content hidden by scrollbars, fixed headers/footers, sticky elements and clipped containers.
- Horizontal/vertical overflow, unexpected wrapping, elements extending outside boundaries and controls hidden below the visible area.
- Nested scrolling only when visibly present; do not infer scrolling behaviour from source code.
- Responsive arrangement only when supported by supplied viewport evidence.

5.15 CROSS-SCREEN CONSISTENCY
- Compare equivalent page headers, toolbars, tables, forms, buttons, badges, fields, dialogs, labels, icon treatments, spacing and visible states.
- Identify each compared screen/component location and the concrete difference.
- Use supplied rules/reference patterns first. Otherwise, report only demonstrable inconsistencies without an apparent purpose.
- Do not standardise intentional differences without evidence.

============================================================
6. SAAS VISUAL DESIGN PRINCIPLES
============================================================

Apply these principles when relevant to the visible component and supported by evidence:

1. CONSISTENCY AND REUSABLE PATTERNS
Equivalent components should use coherent dimensions, spacing, typography, icon treatment, state styling and action placement unless there is a clear purpose for variation.

2. INFORMATION HIERARCHY
Titles, labels, primary values, supporting information and actions should be visually distinguishable according to their role.

3. DATA DENSITY AND SCANNABILITY
Data-heavy screens should remain readable and scannable. Row density, alignment, spacing, grouping and formatting should support comparison without clipping or visual crowding.

4. ALIGNMENT AND SPACING SYSTEM
Related elements should align predictably, with coherent margins, padding, gaps and baselines. Report specific mismatches, not vague preferences.

5. VISUAL AFFORDANCE AND STATE CLARITY
Visible controls and states should be distinguishable in context. Selected, active, disabled, destructive, warning, error and success treatments should not be visually ambiguous where shown.

6. READABILITY AND LEGIBILITY
Text, labels, icons and values should be legible at the inspected size, fit their containers and remain distinguishable from surrounding elements.

7. RESTRAINT AND PURPOSEFUL EMPHASIS
Colour, shadows, borders, badges and decorative emphasis should support meaning and hierarchy rather than create unexplained inconsistency.

8. PREDICTABLE COMPONENT PLACEMENT
Equivalent actions and component regions should appear in consistent, context-appropriate positions when supported by the supplied patterns.

9. COMPONENT COMPLETENESS IN CONTEXT
A component should visibly contain the elements needed for its demonstrated purpose, but do not impose features that were not specified or evidenced.

10. CROSS-MODULE COHERENCE
Related screens should use compatible visual patterns. Distinguish genuine inconsistencies from deliberate module-specific needs.

These principles are evaluation criteria, not a licence to invent missing features or report personal preferences as defects.

============================================================
7. FINDING FORMAT, SEVERITY AND QUALITY RULES
============================================================

Every confirmed finding must state:
- Unique finding ID.
- Severity.
- Exact screen/page and component location.
- Observed condition.
- Concrete visible evidence.
- Impact on readability, interpretation or visible use.
- Specific recommended correction.
- Expected visible result after correction.
- Applicable supplied rule or audit category when relevant.

SEVERITY DEFINITIONS
- Critical: A visible defect makes a major screen or important visible control unusable, or prevents its purpose from being understood. Use sparingly and only with clear evidence.
- High: A substantial visible defect significantly obstructs understanding, identification or use of an important component.
- Medium: A clear issue creates confusion, inconsistency or avoidable effort but does not substantially block use.
- Low: A minor typography, icon, spacing, alignment, wrapping or consistency defect with limited impact.

Severity must reflect observed impact and reach, not personal preference. Explain the reason for severity in the relevant row. Do not assign Critical or High merely because an issue sounds important.

FINDING QUALITY RULES
- Be specific, evidence-led and actionable; avoid generic comments such as “improve spacing” or “looks bad.”
- Separate the observed condition, evidence, impact and correction.
- Do not inflate findings by splitting one defect into duplicates.
- Group repeated instances only when the cause and correction are shared; list all affected locations.
- Keep separate findings when the defects or required corrections materially differ.
- Do not pad the report with general best practices or unrelated redesign ideas.
- Do not present a convention or preference as a definite defect unless supported by supplied rules or a clear visible problem.
- For wording issues, quote the existing text exactly when readable and provide a corrected version. Do not invent intended meaning; qualify copy recommendations that require product/business confirmation.
- Keep confirmed defects separate from unverified observations and inspection limitations.

============================================================
8. MANDATORY REPORT FORMAT — EXACTLY 12 SECTIONS
============================================================

DELIVERY CONTRACT
- Produce one standalone HTML report with embedded CSS and no external dependencies.
- Include exactly 12 numbered sections in the order below.
- Include exactly one primary table in each section: exactly 12 primary tables total.
- Each primary table must have exactly 5 columns and use the exact headings specified below.
- Do not add extra tables, nested tables, per-finding tables, appendices or a thirteenth section.
- Put each finding in a row in the relevant table. Use concise labelled lines within a cell when multiple details are needed.
- If a section has no supported entries, retain its table and include one row explaining that no entries were confirmed from the inspected material. Do not invent content to fill a table.
- All finding IDs, locations, severity counts and cross-references must remain consistent across sections.
- Make tables readable with wrapped long text, clear row separation, sufficient cell padding and legible typography. Do not truncate content to shorten the report.

SECTION 1 — AUDIT OVERVIEW
Purpose: Establish what was audited and the overall result.
Exact columns:
| Overview Item | Details | Evidence / Basis | Scope or Coverage Implication | Notes |
Include rows for prototype/application name, audit objective, supplied screens, inspected screens, viewports/states inspected, inspection approach, confirmed finding count, severity distribution and key limitations. Use “Not supplied” where appropriate; do not guess.

SECTION 2 — PRIORITY FINDINGS REGISTER
Purpose: Provide a concise index of every confirmed finding, ordered by severity and impact.
Exact columns:
| Finding ID / Severity | Exact Screen and Component Location | Finding Title / Observed Issue | Impact | Recommended Correction |
Include one row per confirmed finding. This is an index and does not replace detailed evidence in Section 3.

SECTION 3 — DETAILED FINDINGS AND EVIDENCE
Purpose: Provide the full explanation for every confirmed finding.
Exact columns:
| Finding ID, Severity and Title | Exact Location and Visible State | Observed Condition and Evidence | Why It Matters / Impact | Specific Correction and Expected Result |
Use one row per confirmed finding. Include enough detail to act without a separate narrative. Name screen, route if known, component, sub-region and viewport/state if known. Describe concrete visible evidence and the specific correction. Never fabricate measurements.

SECTION 4 — SCREEN-BY-SCREEN REVIEW
Purpose: Record what was inspected on each screen and screen-level observations.
Exact columns:
| Screen / Route | Viewport and State Inspected | Main Components and Regions Inspected | Specific Screen-Level Observations | Finding IDs and Uninspected Areas |
Use one row per screen/route/meaningfully distinct viewport. Keep observations concrete and screen-specific. List finding IDs. Explicitly state inaccessible regions or states.

SECTION 5 — COMPONENT INVENTORY AND COVERAGE
Purpose: Show which component types and instances were inspected.
Exact columns:
| Screen and Exact Component Location | Component Type / Instance | Presence and State Actually Inspected | Criteria Checked and Coverage | Finding IDs / Inspection Gaps |
Use one row per meaningful component instance or repeated component pattern per screen. Consider only relevant components that actually appear. Do not mark a component fully audited merely because it appears in a screenshot.

SECTION 6 — TABLES, GRIDS AND DATA-DENSE COMPONENTS
Purpose: Deeply inspect tables, grids and dense data components when present.
Exact columns:
| Screen and Exact Table / Grid Location | Element Checked | Specific Visible Observation and Evidence | Impact on Readability / Use | Correction and Related Finding ID |
Check applicable titles/toolbars, headers, widths, header-cell alignment, row density, wrapping/truncation, numeric/date alignment, badges, selection, row actions, sorting/filter affordances where shown, pagination, empty/loading states where visible, sticky elements and overflow. If none are present, state so in one row.

SECTION 7 — FORMS, INPUTS AND ACTION CONTROLS
Purpose: Inspect visible form and action-control presentation without analysing code or hidden logic.
Exact columns:
| Screen and Exact Component Location | Component / Control | Visible Condition and Evidence | Impact / Severity if Confirmed | Specific Visual Correction and Finding ID |
Check labels, required cues where shown, input sizing, placeholders, helper/error presentation, spacing, dropdowns, date/time inputs, checkboxes, radio buttons, switches, button hierarchy, destructive actions, icon-only actions and visible disabled/selected/focused/error states. Do not infer unobserved behaviour.

SECTION 8 — TYPOGRAPHY, ICONOGRAPHY AND VISUAL LEGIBILITY
Purpose: Inspect visible text and icon presentation.
Exact columns:
| Screen and Exact Text / Icon Location | Element and Observed Issue | Concrete Evidence / Comparison | Readability or Recognition Impact | Recommended Correction and Finding ID |
Check heading/body/metadata hierarchy, font size/weight, wrapping, clipping, truncation, casing, abbreviations, visible contrast, numeric/date formatting, icon size/alignment, inconsistent icon styles, ambiguous icon-only controls, badge/chip legibility and visible label/message clarity. Do not claim formal WCAG compliance.

SECTION 9 — CHARTS, CARDS, NAVIGATION AND SPECIALISED COMPONENTS
Purpose: Inspect component types not fully covered in earlier sections.
Exact columns:
| Screen and Exact Component Location | Component Type / Specific Observation | Evidence / Relevant Visible Elements | Impact on Interpretation or Use | Correction and Finding ID |
Consider cards/KPI panels; charts, graphs and bars; axes, legends and labels; tabs and segmented controls; sidebars, breadcrumbs and menus; accordions; modals, drawers, popovers and tooltips; alerts, banners and toasts; pagination; calendars; timelines; progress indicators; avatars; file uploads; media previews; empty states and loading placeholders. Include only components actually present or inspectable.

SECTION 10 — CROSS-SCREEN CONSISTENCY AND REPEATED PATTERNS
Purpose: Compare repeated components or patterns across inspected screens.
Exact columns:
| Pattern / Component and Compared Locations | Expected or Reference Presentation | Specific Difference with Evidence by Location | Impact of the Inconsistency | Standardisation / Correction and Finding IDs |
List precise locations for each comparison. Apply supplied reference rules first; otherwise report only demonstrable inconsistencies between screens. Do not invent a standard.

SECTION 11 — PRIORITISED CORRECTION PLAN
Purpose: Convert confirmed findings into a practical order of work.
Exact columns:
| Order / Priority | Finding IDs and Exact Affected Locations | Specific Change Required | Rationale / Expected Visible Outcome | Dependencies or Notes |
Order by impact, severity, number of affected screens/components and shared-component reach. Keep changes traceable to findings. If one shared-component correction addresses several findings, list all affected instances.

SECTION 12 — LIMITATIONS AND FINAL VALIDATION
Purpose: Disclose inspection gaps and verify report integrity.
Exact columns:
| Check / Limitation ID | Screen, Component or Report Area | Result / What Was or Was Not Inspected | Evidence / Reason | Follow-up Needed or Validation Outcome |
Include checks for inaccessible screens/routes/states; missing viewports/reference material; other limitations; all supplied screens accounted for; unique finding IDs; precise locations; evidence/impact/correction present for every finding; duplicate check; severity totals matching Section 2; IDs consistent across sections; component coverage reflecting actual inspection; and compliance with the out-of-scope restrictions. Use clear results such as Pass, Issue or Limited and explain them.

============================================================
9. LOCATION, TRACEABILITY AND REPORT PRESENTATION RULES
============================================================

LOCATION STANDARD
- Use: [Screen/Page] > [Section/Panel] > [Component] > [Sub-element].
- Add route, viewport and visible state when known.
- Strong example: “Students > Student List > table > Status column > row containing ‘Inactive’ badge.”
- Strong example: “Edit Student modal > footer > Save button and Cancel button.”
- Weak example: “Student screen” or “table looks inconsistent.” Expand vague locations.
- If a route or row identifier is unavailable, use the nearest visible title, label, neighbouring element or position. Never invent identifiers.
- If an issue repeats, list every affected location or enumerate all instances in the same cell.

TRACEABILITY
- Assign stable unique IDs such as F-001, F-002 and so on to confirmed findings.
- Use the same IDs in every section that references a finding.
- Section 2 must include every confirmed finding exactly once.
- Section 3 must contain one detailed row for every confirmed finding.
- The correction plan must reference the relevant finding IDs.
- Severity totals must match the confirmed findings in the register.
- Do not count unverified observations as confirmed findings.

HTML PRESENTATION
- Deliver a single standalone HTML file with embedded CSS.
- No external CSS, JavaScript, fonts, scripts or dependencies.
- Use semantic headings and tables with clear column headers.
- Ensure long text wraps; avoid clipped or horizontally unreadable cells.
- Use readable spacing, clear row separation and restrained visual styling.
- Include the prototype/application name if known, audit date if available from the task context, scope note and limitations.
- Do not add separate tables beyond the 12 required primary tables.

============================================================
10. FINAL SELF-CHECK BEFORE DELIVERY
============================================================

Before delivering the report, verify every item below:
1. Exactly 12 numbered sections are present and in the specified order.
2. Exactly 12 primary tables are present: one per section.
3. Every primary table has exactly 5 columns and the exact prescribed headings.
4. No extra table, nested table, per-finding table, appendix or thirteenth section exists.
5. Every confirmed finding has a unique ID and precise location.
6. Every finding contains an observed condition, concrete evidence, impact and specific correction.
7. Findings are distinct, validated and not inflated by duplicates or personal preferences.
8. Repeated issues list all affected locations where grouped.
9. Finding IDs, severity counts, screen references and correction-plan references agree across sections.
10. Every supplied/accessed screen is accounted for and inspection gaps are disclosed.
11. Component categories are inspected when present; absent components and hidden states are not invented.
12. Responsive findings are based only on actual viewport evidence.
13. No source-code, DOM, implementation, backend, business-logic, security, SEO, performance or general functional analysis is included.
14. The report is one standalone HTML file with embedded CSS and no external dependencies.
15. Section 12 is the final section; no appendix or additional table follows it.

============================================================
FINAL EXECUTION INSTRUCTION
============================================================

Audit the supplied SaaS prototype using this master prompt and any attached project-specific skills, component rules or design references. Treat those references as supporting criteria, not as permission to invent findings. Inspect the actual visible interface, validate each candidate, deduplicate related issues, and generate the required standalone HTML report with exactly 12 sections and 12 tables, each containing exactly 5 columns with the prescribed headings.

Do not modify the prototype. Do not analyse source code or hidden logic. Do not fabricate evidence. Report confirmed defects only as findings, and disclose genuine inspection limitations clearly.
